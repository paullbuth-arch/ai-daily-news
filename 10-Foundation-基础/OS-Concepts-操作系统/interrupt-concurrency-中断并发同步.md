# 中断、并发与同步机制

**一句话结论（20% 核心）**：中断 = CPU 干活时被紧急事件打断，先去处理它再回来；并发 = 多件事看起来同时发生；同步机制 = 防止这些同时发生的事互相踩脚的规则。嵌入式 90% 的 bug 和这三者有关。

---

## 第一层：核心认知（必须先看懂）

### 1.1 中断是什么？——费曼类比：你在家看电视

你正在看电视（主程序）。突然门铃响了（中断请求）。

- 你按下暂停键，记住看到第 23 分钟（**保存现场**）
- 去开门，处理门外的事——拿快递、签收（**执行 ISR**）
- 回来，从第 23 分钟继续看（**恢复现场**）

```
主程序 → [中断发生] → 保存现场 → ISR 处理 → 恢复现场 → 主程序继续
```

**中断 vs 轮询——费曼类比：等快递**

| 方式 | 怎么做 | 优缺点 |
|---|---|---|
| **轮询** | 每 5 分钟去门口看看快递到了没 | 简单，但浪费你的时间（CPU） |
| **中断** | 快递到了门铃响 | 高效省电，但你要能随时放下手头的事 |

**什么时候用中断？** 事件发生时间不确定、CPU 在等的时候可以做别的事。比如 UART 收到数据、按键按下、DMA 搬完数据——这些都用中断。

### 1.2 并发为什么会出问题？——费曼类比：共用一个冰箱

你和室友共用一个冰箱。早上你看冰箱里还有牛奶，决定下楼买面包回来喝。你出门后，室友把牛奶喝光了。你回来发现牛奶没了——你的计划崩了。

**这就是并发 bug 的本质**：你看到的状态，在你使用它之前，被别人改了。

**程序里的例子**：

```c
volatile uint32_t counter = 0;

// 主循环
void main_loop(void) {
    counter++;  // 步骤：①读 counter → ②加 1 → ③写回
}

// UART 中断
void uart_isr(void) {
    counter++;  // 也是读→加→写
}
```

假设 counter 初始是 0：
- 主循环读出 counter = 0，准备加 1
- **此时中断发生！** ISR 读出 counter = 0，加 1 得到 1，写回
- 中断返回，主循环继续：把刚才的 0 加 1 得到 1，写回

**结果 counter = 1，但实际加了两次，应该是 2。** 这就是数据竞争（Data Race）——两个执行流同时修改一个变量，其中一个的修改被另一个覆盖了。

### 1.3 同步机制：怎么避免打架？

**费曼类比**：火车上的厕所门锁。

- 有人进去 → 锁门（**获取锁**）
- 外面的人进不来 → 等着（**阻塞**）
- 里面的人出来 → 开锁（**释放锁**）
- 下一个人进去

嵌入式里常用的同步手段：

| 机制 | 一句话 | 什么时候用 | 什么时候不能用 |
|---|---|---|---|
| **关中断** | 暂时禁止所有中断 | 保护一段很短的共享数据访问 | 关太久会让系统失去响应 |
| **互斥量（Mutex）** | 任务间的锁，同一时刻只有一个任务能持有 | 多个任务共享 I2C 总线、共享配置结构体 | 中断里不能用！ |
| **信号量（Semaphore）** | 计数器，用于通知"有资源了" | ISR 通知任务"数据到了"，任务等待资源 | 不适合传数据，只适合传信号 |
| **队列（Queue）** | ISR 和任务之间传递数据的管道 | UART 收到数据 → 放入队列 → 任务取出处理 | 数据量极大时用环形缓冲区更高效 |

**最重要的规则**：
- **ISR 里不能做的事**：等锁（会死锁）、调用可能阻塞的函数（printf/malloc）、延时
- **ISR 里能做的事**：读寄存器、写缓冲区、发信号量唤醒任务、设置标志位

### 1.4 最小代码示例

```c
// 经典模式：ISR 收数据 → 发信号量 → 任务处理
SemaphoreHandle_t data_ready_sem;

void uart_isr(void) {
    uint8_t byte = UART_DATA_REG;
    rx_buf[rx_head++] = byte;
    // 在 ISR 中发信号量：不阻塞，只通知
    BaseType_t wake = pdFALSE;
    xSemaphoreGiveFromISR(data_ready_sem, &wake);
    portYIELD_FROM_ISR(wake);  // 如果需要切换任务，在这里触发
}

void process_task(void *p) {
    for (;;) {
        // 等待信号量：没数据就阻塞，不浪费 CPU
        if (xSemaphoreTake(data_ready_sem, portMAX_DELAY)) {
            // 处理 rx_buf 中的数据
            process_data();
        }
    }
}
```

### 1.5 如果只记得一件事

> 中断打断主程序，并发导致数据竞争，同步机制（关中断/互斥量/信号量/队列）防止竞争。ISR 里不能阻塞、不能等锁、不能延时。ISR 只负责"收数据 + 发通知"，任务负责"处理数据"。

## 第二层：实战理解

### 2.1 临界区：保护共享数据的最短代码段

```c
// 临界区 = 关中断 → 访问共享数据 → 恢复中断
// 必须非常短！通常只有几行代码

uint32_t save = irq_disable_save();  // 关中断 + 保存旧状态
shared_counter++;                     // 安全地修改共享变量
irq_restore(save);                    // 恢复中断状态
```

**关键点**：
- 临界区里的代码越短越好（通常 < 10 行，不要有循环）
- 保存/恢复中断状态，而不是简单地"开中断"——因为调用这个函数前中断可能本来就是关的
- 临界区嵌套时要小心：不能在里面调用可能阻塞的函数

### 2.2 优先级反转：高优先级任务被低优先级任务卡住

**费曼类比**：三个打工人抢会议室。

- **小 A**（低优先级）：正在用会议室
- **小 B**（中优先级）：在普通工位干活
- **小 C**（高优先级）：急需用会议室

小 C 等着小 A 出来。但小 B 一直在干活（CPU 优先给小 B），小 A 抢不到 CPU 出不来。结果：**最高优先级的小 C 被最低优先级的小 A 和中优先级的小 B 一起卡住了**。

**解决方法**：优先级继承——小 A 持有锁期间，临时提升到小 C 的优先级，等释放锁后再降回来。FreeRTOS 的互斥量默认支持优先级继承。

### 2.3 环形缓冲区：ISR 和任务之间无锁传数据

这是嵌入式里最经典的数据结构。核心思想：**ISR 只写 head，任务只读 tail，双方各改各的指针，不需要锁**。

```c
// 关键设计：head 只由 ISR 写，tail 只由任务写
// 双方只读对方的指针，不修改
typedef struct {
    uint8_t  buf[256];           // 大小必须是 2 的幂
    volatile uint32_t head;      // ISR 写入位置
    volatile uint32_t tail;      // 任务读取位置
} rbuf_t;

// ISR 中调用：写入一个字节
bool rbuf_put(rbuf_t *rb, uint8_t data) {
    if (rb->head - rb->tail == 256) return false;  // 满了
    rb->buf[rb->head & 0xFF] = data;
    rb->head++;
    return true;
}

// 任务中调用：读取一个字节
bool rbuf_get(rbuf_t *rb, uint8_t *data) {
    if (rb->head == rb->tail) return false;  // 空了
    *data = rb->buf[rb->tail & 0xFF];
    rb->tail++;
    return true;
}
```

## 第三层：深入扩展

### 3.1 FreeRTOS 的临界区实现

```c
// 任务中进入临界区：关闭中断或挂起调度器
taskENTER_CRITICAL();
// 访问共享资源
taskEXIT_CRITICAL();

// ISR 中进入临界区
UBaseType_t uxSavedInterruptStatus;
uxSavedInterruptStatus = taskENTER_CRITICAL_FROM_ISR();
taskEXIT_CRITICAL_FROM_ISR(uxSavedInterruptStatus);
```

### 3.2 原子操作：CPU 保证不会被打断的读写

```c
// 普通 counter++ 不是原子的（读→改→写三步）
// 原子操作保证不被中断打断
__atomic_add_fetch(&counter, 1, __ATOMIC_SEQ_CST);
```

适合对单个变量做简单的加减、位操作。复杂的数据结构还是需要锁。

### 3.3 常见问题

- **中断和轮询的区别？什么时候用中断？** 中断是事件驱动（门铃），轮询是主动查询（不停看门口）。事件发生时间不确定、频率低时用中断；高频事件（如音频采样）用 DMA。
- **为什么 ISR 里不能调用 printf？** printf 可能阻塞（等待 UART 发送完成），而 ISR 不能阻塞。且 printf 通常不可重入。
- **什么是数据竞争？** 两个执行流同时访问同一变量，至少一个是写操作，且没有同步保护。
- **volatile 能替代锁吗？** 不能。volatile 只保证每次从内存读，不保证读-改-写的原子性。
- **优先级反转怎么解决？** 优先级继承：持有锁的低优先级任务临时提升到等待者的优先级。

### 3.4 核心术语表

| 英文 | 中文 | 一句话 |
|---|---|---|
| ISR | 中断服务程序 | 中断发生时执行的函数 |
| IRQ | 中断请求 | 硬件发出的中断信号 |
| Race Condition | 竞态条件 | 程序结果取决于执行时序 |
| Data Race | 数据竞争 | 两个执行流同时写同一变量 |
| Critical Section | 临界区 | 关中断保护的一段代码 |
| Mutex | 互斥量 | 任务间的锁，一次只有一个持有者 |
| Semaphore | 信号量 | 资源计数器，用于通知和同步 |
| Queue | 队列 | 任务间传数据的管道 |
| Priority Inversion | 优先级反转 | 高优先级任务被低优先级任务阻塞 |
| Priority Inheritance | 优先级继承 | 临时提升锁持有者的优先级 |
| Atomic Operation | 原子操作 | CPU 保证不可分割的操作 |
| Reentrant | 可重入 | 函数可以安全地被多个执行流同时调用 |
