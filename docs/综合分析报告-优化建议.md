# 货脉 App 综合分析报告与优化建议

> 文档版本：v1.1
> 修订日期：2026-07-01
> 适用版本：货脉 v2.7.0 / Flutter + Dart
> 修订说明：本版已按当前代码状态修正旧版误判，删除“机掌柜”、登录认证、ScanPage 不可回退、订单统计不联动、StatusChip 重复定义等过期结论。

---

## 一、总体判断

货脉当前已经具备较完整的二手 iPad 经营工作流：收货入库、AI 识别、库存管理、售出、订单、售后、批发价导入、闲鱼文案、经营复盘、备份与 WebDAV 同步都已经成型。

后续优化不应再按“从零补功能”的方式推进，而应围绕三个方向收敛：

| 方向 | 目标 | 优先级 |
|------|------|--------|
| 业务效率 | 让库存、订单、批发价、闲鱼发布这些高频动作更少点、更少跳转 | 高 |
| 数据安全 | 避免误删、覆盖、同步冲突、未保存离开造成损失 | 高 |
| 体验一致性 | 统一输入、选择、弹层、列表、卡片和图表表达 | 中 |

当前不建议优先做大规模技术栈替换。Flutter 仍可支撑现有产品，但需要控制高开销视觉效果、减少不必要重绘，并逐步把状态刷新从 GlobalKey 手动调用迁移到更统一的事件/状态机制。

## 二、已修正的旧结论

以下结论在旧文档中出现，但与当前代码或产品方向不完全一致，后续不应作为待办直接执行。

| 旧结论 | 当前判断 |
|--------|----------|
| 应用仍叫“机掌柜” | 已更名为“货脉”，文案、备份、导出等多数位置已改为货脉 |
| ScanPage 步骤不可回退 | 当前已有上一步逻辑，不是问题 |
| 订单筛选后统计未更新 | 当前订单页先筛选再统计，结论不成立 |
| StatusChip 在 page_scaffold.dart 和 chips.dart 重复定义 | 当前正式组件只在 chips.dart，旧结论疑似来自备份文件 |
| 登录认证需要继续完善 | 当前产品已按需求屏蔽登录，短期不应把账号体系作为主线 |
| AI 完全无历史记录 | 闲鱼文案已有规则和样例库，但通用 AI 调用历史仍可后续补 |
| Light Theme 是高优先级 | 当前产品主视觉是深色风格，浅色主题不是近期核心目标 |

## 三、当前产品结构

| 模块 | 当前能力 | 主要短板 |
|------|----------|----------|
| 首页 | 经营看板、搜索、快捷入口、利润趋势 | 部分快捷动作仍可更顺手，搜索体验可继续优化 |
| 扫码收货 | 关于本机 AI 识别、手动录入、图片、自动定价、文案生成 | AI 失败后的纠错和补录引导还可加强 |
| 库存管理 | 库存/在售列表、型号筛选、关键词搜索、卡片操作 | 缺排序、多维筛选、批量操作 |

| 设置/备份 | AI 配置、WebDAV、备份恢复、清空数据 | 恢复/清空/同步需要更强校验和二次确认 |

## 四、重点问题与优化建议

### 4.1 库存管理

库存是当前最值得继续优化的核心页面。真实经营场景里，设备一多，单纯按型号和关键词筛选会不够用。

| 问题 | 建议 | 优先级 |
|------|------|--------|
| 缺少排序 | 增加按入库时间、库龄、采购价、售价、毛利、型号排序 | 高 |
| 筛选维度偏少 | 增加成色、电池健康、网络版本、容量、价格区间、状态组合筛选 | 高 |
| 缺少批量操作 | 支持批量上架、下架、下载素材、导出、修改状态 | 中高 |
| 卡片信息密度可优化 | 卡片上适度展示成本、售价、库龄、预计毛利，不要塞太满 | 中 |

建议先做“排序 + 多维筛选”，再做批量操作。排序和筛选能立刻提升找货效率，改动范围也更可控。

### 4.2 商品详情

商品详情已经从“点按钮编辑”改为直接在框内修改，这是正确方向。下一步重点不是再加复杂页面，而是保护数据和统一输入体验。

| 问题 | 建议 | 优先级 |
|------|------|--------|
| 未保存离开风险 | 有修改但未保存时，返回前弹出保存/放弃选择 | 高 |
| 字段输入方式不统一 | 容量、颜色、网络、成色、日期等优先用选择器或日期选择，不强迫手输 | 高 |
| 信息排列占空间 | 字段名放入输入框 label/hint，不额外占左侧一列 | 高 |
| AI 描述可继续增强 | 允许基于当前设备信息重新生成，并保留用户手改内容 | 中 |

### 4.3 订单管理

订单页当前统计逻辑是正确的，旧文档中“筛选后统计未更新”应删除。真正缺的是查找和风险提醒。

| 问题 | 建议 | 优先级 |
|------|------|--------|
| 无订单搜索 | 按买家、设备、序列号、平台、日期范围搜索 | 高 |
| 待发货无提醒 | 超过设定天数未发货时标注提醒 | 中 |
| 售后追踪较轻 | 增加售后进度、原因、费用、处理结果记录 | 中 |
| 订单卡片信息略少 | 补设备关键信息，避免点进详情才知道是哪台 | 中 |

### 4.4 今日批发价与视觉识别

今日批发价图片导入已经支持 AI 识别和表格核对，这是正确方向。后续重点是让 AI 更懂这类图片的业务结构。

| 问题 | 建议 | 优先级 |
|------|------|--------|
| 同型号多价格识别容易漏 | Prompt 明确要求同型号不同成色/容量/网络/备注都拆成独立行 | 高 |
| 图片版式不固定 | 要求 AI 先理解表头、分组、备注、跨行关系，再输出标准表格 | 高 |
| 识别结果缺少异常检查 | 对离群价格、缺型号、缺价格、重复型号给出提示 | 中 |
| 反向核对链路可加强 | 保留本次识别原始表格，支持导出 CSV/Excel 复核 | 中 |

建议把“AI 识图”当成结构化录入助手，不要只让它输出型号和价格。目标输出字段应至少包含：型号、容量、网络、颜色、成色/备注、价格、来源日期、置信度或异常说明。

### 4.5 AI 经营日报与采购决策

用户已经反馈 AI 日报和采购决策偏鸡肋。问题不在于模型不够强，而是产品形态太像“生成一段报告”，离真实动作还差一步。

闲鱼文案方向已经有更明确的训练来源：`docs/闲鱼iPad文案素材50条.md` 不应原样照抄，而应提炼为风格规则和安全样本。当前建议把它作为默认表达素材来源，并结合本店已售文案持续修正。

| 文案素材处理 | 说明 |
|--------------|------|
| 50 条素材 | 归纳为性价比、真实自用、专业参数、学生学习、办公生产力、追剧娱乐、实用主义等风格 |
| 风险表达 | 全新、假一赔十、包退、付费账号、学习资料、官方在保等内容必须按真实设备信息决定是否可写 |
| 生成原则 | AI 只学习表达节奏，不带入样本中的价格、瑕疵、配件、个人经历或承诺 |
| 真实反馈 | 已售设备文案、成交快慢、售后情况应继续进入经验库，权重高于通用素材 |

建议调整为：

| 方向 | 说明 |
|------|------|
| 本地规则先算 | 先用库存、成交、库龄、行情差价算出明确结论 |
| AI 只做复核和表达 | AI 负责解释原因、生成谈价话术、提醒风险 |
| 输出动作而不是报告 | 比如“这 3 台应降价”“这 2 个型号今天不建议收”“这个报价最多压到多少” |
| 保留人工决策入口 | AI 建议旁边提供采纳、忽略、稍后处理 |

### 4.6 数据安全与同步

当前本地 JSON + 备份 + WebDAV 的方向可以继续用，但要加强保护。

| 问题 | 建议 | 优先级 |
|------|------|--------|
| 单文件 JSON 损坏风险 | 保存前校验、保存后备份，失败时回滚上一份可用数据 | 高 |
| 清空数据风险高 | 清空前自动备份，确认后再执行，并显示清空范围 | 高 |
| WebDAV 覆盖风险 | 增加本地/云端更新时间、设备标识、冲突提示 | 中高 |
| 恢复备份风险 | 恢复前检查 JSON 结构和版本，恢复后给出摘要 | 中 |
| 数据版本迁移弱 | 在数据文件中明确 schemaVersion，升级时执行迁移 | 中 |

SQLite 可以作为长期方向，但短期更重要的是：先把现有 JSON 的备份、校验、恢复和冲突处理做扎实。

### 4.7 UI 与交互一致性

当前视觉风格已经形成识别度，后续不建议大改风格，而是统一控件行为。

| 问题 | 建议 | 优先级 |
|------|------|--------|
| 输入和选择体验不完全统一 | 参考“今日批发价”的输入/选择方式，抽成统一表单模式 | 高 |
| 部分二级界面仍像临时弹窗 | 表单类使用统一底部面板或页面内展开，不再混用透明弹框 | 中高 |
| 字段 label 占空间 | 移入输入框 label/hint，移动端节省横向空间 | 中高 |
| 毛玻璃/阴影可能影响高刷流畅度 | 对长列表减少 BackdropFilter、阴影和大面积渐变重绘 | 中 |
| 颜色和间距仍有硬编码 | 新页面优先使用 C 常量和组件库，旧页面逐步整理 | 中 |

浅色主题暂不列为近期重点。除非未来明确要支持白天户外使用，否则当前应优先保持深色主视觉的一致性和性能。

### 4.8 状态管理与架构

当前 MainShell 通过 GlobalKey 触发 Home/Stock/Order 刷新，能用，但耦合偏强。

| 问题 | 建议 | 优先级 |
|------|------|--------|
| 页面刷新依赖 GlobalKey | 短期加一个轻量数据变更通知机制 | 中 |
| 页面各自 setState 刷新 | 把库存、订单、统计的刷新入口收敛 | 中 |
| 引入 Riverpod 成本较高 | 暂不立即全量迁移，等业务功能稳定后分模块替换 | 低 |

建议先做轻量事件通知，不要现在就为了架构漂亮进行大范围重构。

## 五、推荐排期

### 第一阶段：近期优先

| 事项 | 原因 |
|------|------|
| 库存排序与多维筛选 | 直接提升找货和管理效率 |
| 订单搜索 | 订单增加后必需 |
| 商品详情未保存离开提醒 | 避免数据丢失 |
| 商品详情字段选择器统一 | 改善移动端录入效率 |
| 今日批发价 OCR Prompt 和异常校验增强 | 降低识别错误带来的价格风险 |
| 清空数据/恢复备份前自动校验和备份 | 防止不可逆损失 |

### 第二阶段：中期迭代

| 事项 | 原因 |
|------|------|
| 库存批量操作 | 提升批量上架、下载、导出的效率 |
| 待发货和滞销提醒 | 从记录工具升级为经营助手 |
| AI 经营建议改为动作清单 | 解决 AI 日报鸡肋问题 |
| WebDAV 冲突检测 | 降低多设备同步覆盖风险 |
| 统一表单/选择组件 | 让所有二级界面风格一致 |

### 第三阶段：长期规划

| 事项 | 原因 |
|------|------|
| schemaVersion + 数据迁移 | 为长期迭代打基础 |
| SQLite 或分表存储 | 数据量明显增大后再做 |
| Riverpod 等状态管理迁移 | 等页面和业务流程稳定后逐步替换 |
| 完整浅色主题 | 只有确认有真实使用需求时再投入 |

## 六、不建议近期投入的事项

| 事项 | 原因 |
|------|------|
| 重新做登录系统 | 当前已经按产品需求屏蔽登录，短期没有必要 |
| 全量更换技术栈 | 成本高，且当前问题主要是局部性能和交互，不是 Flutter 无法实现 |
| 为了架构一次性重构全项目 | 容易影响已稳定业务流程 |
| 大规模改视觉风格 | 当前风格已被认可，应做一致性和细节优化 |
| 把 AI 做成单独“大工作台” | 容易变空泛，应该嵌入库存、采购、文案、订单这些具体场景 |

## 八、结论

这份报告修正后，应作为“货脉 v2.7.0 后续优化路线图”，而不是单纯的问题清单。

近期最值得做的是库存效率、订单搜索、商品详情数据保护、批发价 OCR 准确性和数据安全。架构升级、浅色主题、SQLite、Riverpod 都可以规划，但不应抢在核心经营体验前面。
